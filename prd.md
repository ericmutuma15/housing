# Product Requirements Document (PRD)

**Title:** Integrated Dashboard Suite — Data Analysis, GIS & Inventory

**Project Owner / Sponsor:** ICT Department — State Department for Urban Development & Housing (Kenya)

**Prepared for:** Contractor teams building housing solutions for Kenyan citizens

**Date:** 2026-02-03

---

## 1. Purpose & Executive Summary

Build an integrated full-stack web application that provides three embedded dashboards in a single portal: a Data Analysis dashboard, a GIS (spatial) dashboard, and an Inventory dashboard with administrative rights. The system will help the ICT Department and contractors plan, monitor and report on housing development projects across Kenya by combining tabular analysis, spatial insights, and inventory management.

This PRD captures the minimum product requirements, technical choices, integration points (Power BI live link), and an implementation roadmap. The application is intended as a production-capable system but will support autogenerated mock data for demonstration and stakeholder validation prior to final data availability.

---

## 2. Goals & Success Metrics

**Primary goals**
- Provide fast, filterable data analysis views (category, year, occupied/not occupied) for project and unit-level insights.
- Deliver a powerful GIS view that visualizes spatial distribution and differences across categories (choropleth, heatmaps, clustering).
- Offer a full-featured inventory dashboard with CRUD operations guarded by RBAC for administrators.
- Embed an externally maintained Power BI dashboard via a live link for high-level executive reporting.
- Produce downloadable summary reports based on the current dataset and active filters.

**Success metrics**
- Stakeholder demo acceptance within 2 sprints using mock data.
- Dashboard load time: <3s for summary visualizations; interactive map loads <5s over broadband.
- Role-based access enforced 100%; no unauthorized CRUD allowed.
- Report generation time <10s for datasets up to 100k rows.

---

## 3. Stakeholders & Users

- **Primary:** ICT Department analysts and managers, project contractors, operations teams.
- **Secondary:** Executive decision-makers (via Power BI), procurement/logistics teams, field officers.

**User roles & personas**
- **Viewer (Default user):** Can view dashboards, apply filters, download reports.
- **Analyst:** Viewer + ability to export data subsets and run deeper visualizations.
- **Inventory Manager (Privileged):** Analyst + add/update/delete inventory items and categories.
- **Admin:** Full system rights (manage users, roles, integrations, API keys).

---

## 4. Scope & Assumptions

**In scope (Minimum Viable Product):**
- React (Vite) frontend embedding three dashboards within a single UI.
- FastAPI backend (Python) exposing RESTful endpoints, authentication (JWT / OAuth2), and data APIs.
- PostgreSQL with PostGIS extensions for spatial functionality.
- Power BI dashboard embedding via live link (iFrame or Power BI embedding mechanism) with appropriate auth.
- Data visualizations using Python libraries (Plotly/Bokeh/Altair for modern interactive visuals), surfaced to React.
- Autogeneration of mock data (Faker, GeoJSON generators) for demos.
- Deployment: backend on Render, frontend on Vercel. CI/CD via GitHub Actions.

**Out of scope (initial release):**
- Mobile-first native apps (responsive web only).
- Full ETL pipelines from legacy government systems (to be planned later).

**Assumptions:**
- Final production data schema is not yet available; mock data will be used for design and demos.
- Power BI report is prepared by the reporting team and accessible via a sharable live link or embedding token.
- The environment supports PostGIS on managed PostgreSQL.

---

## 5. Technology Stack

- **Frontend:** React (Vite) + TypeScript, react-router, react-query, react-plotly.js, leaflet or Mapbox GL JS for mapping, Tailwind CSS for styling.
- **Backend:** Python (FastAPI), Uvicorn/Gunicorn, SQLAlchemy or Tortoise ORM, psycopg2 / asyncpg.
- **Database:** PostgreSQL with PostGIS extension.
- **GIS tools/integration:** Google Earth Engine (for large raster/remote sensing tasks), QGIS for offline analyses and generating layers, GeoJSON for vector exchange.
- **Charts/visuals:** Plotly (interactive), Bokeh or Altair (optional) for server-side visuals if desired. Folium for quick maps (server-side), but prefer client-side mapping for interactivity.
- **Power BI embedding:** Power BI live link or Power BI Embedded (depending on licensing). Use secure token or designated public embed link per organizational policy.
- **Hosting & CI/CD:** Backend on Render; Frontend on Vercel; GitHub Actions for build/test/deploy.
- **Authentication:** OAuth2 or OpenID Connect for SSO (where available), fallback to JWT-based auth.
- **Mock data:** Faker (Python) + custom GeoJSON generator; ability to seed DB with commands.

## 6. Data & Schema (Placeholder)

> Note: Schema will be finalized once real data is available. Below are suggested tables and spatial columns to guide development and mock data generation.

**Suggested tables (high-level)**
- `users` — id, name, email, role, hashed_password, organisation, last_login
- `projects` — id, name, start_date, end_date, status, budget, region_id
- `units` — id, project_id, unit_type, status (occupied/not), build_year, geo_location (geometry Point/Polygon)
- `inventory_items` — id, sku, name, category, quantity, unit_cost, location_id, last_updated
- `locations` — id, name, region_code, boundary (geometry Polygon)
- `events` — id, unit_id, event_type, timestamp, details

**Spatial requirements**
- Use PostGIS geometry/geography columns (e.g., `geometry(Point, 4326)` for units, `geometry(Polygon, 4326)` for locations).
- Export/ingest via GeoJSON, Shapefile (via QGIS), or WKT.

**Mock data plan**
- Build a `manage.py seed --env=demo` script that uses Faker and randomized spatial generators to create:
  - 1,000 — 10,000 units with random coordinates within Kenya bounding box and assigned categories/status.
  - ~100 projects across county/region boundaries.
  - Inventory items across warehouses and sites.
- Generate GeoJSON layers representing administrative boundaries (counties/wards) for choropleth maps.

## 7. Functional Requirements

### 7.1 Common
- FR1: Users must log in using SSO/OAuth2 or local credentials.
- FR2: RBAC enforced on every API endpoint and UI action.
- FR3: All dashboards should support filters: category, year, occupied/not occupied, region, project.
- FR4: Export current view to CSV and generate downloadable PDF summary reports.

### 7.2 Data Analysis Dashboard
- FR5: Display key KPIs (counts, rates, year-on-year change) in top summary cards.
- FR6: Data visualizations: time series, bar charts, stacked bars, box plots, and a configurable data table (sortable & searchable).
- FR7: Re-render visuals when filters are changed and allow saving filter presets.
- FR8: Allow drilling down from aggregated chart to individual records.
- FR9: Integrate modern Python visuals: backend endpoints return Plotly JSON objects which the frontend renders with `react-plotly.js`, or return pre-rendered images for simpler clients.

### 7.3 GIS Dashboard
- FR10: Interactive map showing units, projects, and administrative boundaries.
- FR11: Visual types: choropleth (by category or occupancy rate), heat map (density of units), cluster markers for large datasets, and choropleth overlays for region-level stats.
- FR12: Ability to toggle layers (units, projects, inventory locations, county/ward boundaries).
- FR13: Popup detail when clicking a unit/project with key attributes and link to record.
- FR14: Spatial filters: draw-box / polygon selection, radius search from a point, filter by attribute.
- FR15: Support GeoJSON export of current selection and one-click open in QGIS.
- FR16: Connect to Google Earth Engine for raster analysis workflows (e.g., NDVI, landcover) — background process or scheduled job.

### 7.4 Inventory Dashboard
- FR17: Inventory summary and low-stock alerts.
- FR18: Inventory list view with pagination, filters (category, location, status), inline quick edits.
- FR19: Inventory managers and admins can create/read/update/delete items (CRUD) — all actions auditable.
- FR20: Allow bulk import/export via CSV for inventory items.
- FR21: Simple forecasting (basic): average consumption rate per period and projected depletion date.

### 7.5 Reporting
- FR22: Report generator that analyses current filters and dataset and produces a downloadable PDF containing charts and summary tables.
- FR23: Provide export options: CSV, XLSX, PDF. Generated reports include metadata (filters used, generation time, user id).
- FR24: Option to schedule recurring reports (email delivery) — stretch goal for Phase 2.

## 8. Non-Functional Requirements

- NFR1: Use HTTPS everywhere; all deploys must enforce TLS.
- NFR2: Authentication tokens expire and support refresh tokens.
- NFR3: Logging and monitoring — error logs persisted, basic dashboard for application health.
- NFR4: Backups — nightly DB backups and point-in-time restore strategy.
- NFR5: Scalability — horizontally scale backend on Render; database sizing planned for expected dataset sizes.
- NFR6: Performance — APIs for chart data respond within 2s for aggregated queries; map tile / vector data respond within 5s.
- NFR7: Accessibility — meet WCAG AA for dashboard controls and charts where possible.
- NFR8: Security — RBAC, input validation, parameterized SQL to avoid injections, rate limiting on critical endpoints.

## 9. Integration & External Systems

- **Power BI:** Embed live dashboard via secure embed link; ensure CORS and CSP headers allow the embed. Coordinate with reporting team for tokens and embed URLs.
- **Google Earth Engine (GEE):** Used for heavy raster/remote sensing analyses. GEE jobs run server-side; results returned as GeoTIFFs or vector overlays.
- **QGIS:** Export/import support via GeoJSON/ESRI Shapefile; provide clear export instructions from the GIS dashboard.

## 10. API & Endpoints (Example)

- `POST /auth/login` — returns JWT
- `POST /auth/refresh` — refresh token
- `GET /api/kpis` — returns summary KPIs for dashboard
- `GET /api/analysis?category=&year=&occupied=` — returns Plotly JSON / data payload
- `GET /api/units` — paginated units endpoint (supports spatial filtering)
- `GET /api/units/{id}` — unit detail
- `POST /api/inventory` — create item (admin/inventory-manager)
- `PUT /api/inventory/{id}` — update item
- `DELETE /api/inventory/{id}` — delete item
- `POST /api/reports/generate` — generate report (PDF/CSV) for current filters

> Note: All endpoints require authentication except for public embed endpoints (if the organization permits public access to Power BI link).

## 11. Data Migration & Mock Data Strategy

- Implement `seed` utilities that generate:
  - realistic attribute distributions (occupation rates per region, build years, unit types).
  - geo-coherent points (snap to county centroids and jitter within polygons) to support realistic map visuals.
- Provide `seed --scale` to control dataset size for performance testing.
- Create sample GeoJSON files for administrative units to support choropleth maps.

---

## 12. UI / UX Considerations

- Single-page application (SPA) with a top navigation and three main routes/tabs:
  - `/analysis` — Data Analysis Dashboard
  - `/gis` — GIS Dashboard
  - `/inventory` — Inventory Dashboard
- Responsive layout but optimized for desktop analysts (large screens).
- Use modern card/grid layout for KPI cards and large, full-bleed maps for the GIS view.
- Provide persistent filter bar across dashboards to maintain user context.
- Include a small help & documentation modal describing available filters and dataset notes (especially useful with mock data).

## 13. Deployment & Operations

- **Backend:** Deploy FastAPI app on Render with automatic deploys from `main` branch.
- **Frontend:** Deploy React (Vite) app on Vercel; environment variables for API base URL and Power BI embed link.
- **DB:** Managed PostgreSQL (enable PostGIS) — snapshots and backups configured.
- **CI/CD:** GitHub Actions: test -> lint -> build -> deploy for both frontend & backend.

## 14. Testing & QA

- API contract tests (e.g., using pytest + httpx for FastAPI).

- E2E tests with Cypress covering login, filter flows, map interactions, inventory CRUD.

## 15. Privacy, Compliance & Security

- Follow government standards for data retention and privacy. Personally identifiable information (PII) must be minimized and encrypted at rest.
- Use organization SSO where possible to avoid duplicative credential storage.
- Role-based access reviews and an audit trail for CRUD actions on inventory and sensitive edits.

## 16. Roadmap & Milestones (Suggested)

## 17. Risks & Mitigations

- **Data schema uncertainty** — Mitigation: design adaptable schema and robust seed data; keep migration scripts ready.
- **Power BI embedding limitations / licensing** — Mitigation: confirm licensing early; fallback to exported images if embed is restricted.
- **GIS performance with many points** — Mitigation: use clustering, server-side tiling, and vector simplification.
- **Integration delays with GEE or third-party systems** — Mitigation: mock expected outputs for initial demos.

---

## 18. Acceptance Criteria (MVP)

- Users can log in and view the three dashboard tabs.
- Data Analysis dashboard updates charts when filters (category/year/occupied) change.
- GIS dashboard displays unit points and one choropleth layer; clicking a unit shows details.
- Inventory dashboard lists items; admin user can perform CRUD operations and changes are audited.
- Power BI dashboard is embedded and viewable from within the app via the provided link.
- Reports can be generated and downloaded (PDF/CSV) summarizing the active filters.
